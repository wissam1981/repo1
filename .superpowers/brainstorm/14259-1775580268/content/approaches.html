Architecture Approaches

How should we structure the multi-platform remote control app?

A

Protocol Abstraction Layer (Recommended)

A unified TVProtocol interface with platform-specific drivers behind it. The UI talks to one API — the driver handles platform differences.

Pros

  • Clean separation — UI never knows which platform it's talking to
  • Adding a new platform = adding a new driver, no UI changes
  • Easy to test each driver independently
  • Context-adaptive UI works naturally — drivers report TV state uniformly

Cons

  • Upfront abstraction design takes thought
  • Some platform-specific features may not fit the common interface
B

Platform-Specific Views

Each TV platform gets its own UI and connection logic. Shared only at the design-system level (colors, fonts, components).

Pros

  • Can leverage platform-specific features fully
  • Simpler to start — no abstraction needed
  • Each platform can have a tailored experience

Cons

  • Massive code duplication across 5 platforms
  • Every UI change must be replicated 5 times
  • Context-adaptive UI is harder — different state models per platform
C

Hybrid — Shared UI + Platform Modules (SPM)

Each platform is a Swift Package. A thin orchestrator picks the right package at runtime. UI is shared but can be extended per platform.

Pros

  • Best modularity — platforms can be developed/tested in isolation
  • SPM packages can be reused in other apps
  • Build times improve — only compile what you need

Cons

  • Most complex setup
  • Package dependency management overhead
  • Overkill if you're a solo developer
